# 第 8 章 · 存储期、链接与对象模型

> **卷一 · 语言**　|　前置知识：第 1–7 章　|　建议用时：60 分钟

> 一个对象不只属于某个作用域，它还属于某个存储期、某个链接类别，以及某个翻译单元。

类让单个对象有了生命期，链接让多个翻译单元拼成一个程序。这一章从对象模型的角度回答三个问题：

1. 对象什么时候创建，什么时候销毁？（存储期）
2. 同一个名字在不同翻译单元里是不是同一个对象？（链接）
3. 一个定义可以出现几次？头文件里应该放什么？（ODR）

这些问题在单文件程序里几乎看不见，一旦项目分成多个 `.cpp`，它们就会以“重复定义”“未定义引用”“静态初始化顺序”的形式冒出来。

## 8.1 本章语法地图

| 语法 | 本章出现的位置 |
|------|----------------|
| 自动存储期 | 局部变量 |
| 静态存储期 | 全局变量、`static` 局部变量 |
| 线程存储期 | `thread_local` |
| 动态存储期 | `new` / `delete`、智能指针 |
| 外部链接 | 非 `static` 的全局变量/函数 |
| 内部链接 | `static` 全局变量、匿名命名空间、文件作用域 `const` |
| `extern` | 声明别处定义的对象 |
| `static` | 内部链接或静态局部变量 |
| 匿名命名空间 | 翻译单元内可见 |
| `inline` 变量 | C++17，头文件中可定义 |
| 头文件保护 | `#ifndef` / `#define` / `#endif` |
| ODR | 一次定义规则 |

## 8.2 四个维度

描述一个名字/对象时，至少有四个维度：

| 维度 | 问题 | 例子 |
|------|------|------|
| 作用域（scope） | 名字在源码的哪里可见？ | 块作用域、命名空间作用域 |
| 存储期（storage duration） | 对象的存储什么时候分配、什么时候释放？ | 自动、静态、线程、动态 |
| 链接（linkage） | 不同翻译单元能否看到同一个名字？ | 外部、内部、无链接 |
| 生命期（lifetime） | 对象从构造到析构的时间段 | 与存储期相关，但类类型有构造/析构 |

这四个维度经常被混为一谈。`static` 尤其容易：它在不同位置有不同含义。

## 8.3 存储期

### 自动存储期

局部变量默认是自动存储期：

```cpp
void f()
{
    int value = 42;   // 进入作用域时创建，离开时销毁
}
```

每次调用 `f()`，`value` 都是一个新对象；函数返回时，它的存储被回收。自动对象的生命期与作用域绑定。

### 静态存储期

全局变量、命名空间作用域的变量、`static` 局部变量有静态存储期：

```cpp
int global = 1;          // 程序启动时创建，程序结束时销毁

void f()
{
    static int count = 0; // 第一次执行到此处时初始化，之后一直存在
    ++count;
}
```

静态存储期的对象在程序整个运行期间都存在。它们的初始化时机：

- 常量初始化（零初始化、常量表达式初始化）在程序启动前完成；
- 动态初始化（需要运行期计算的构造函数）在 `main` 之前或第一次经过声明时完成，具体顺序在跨翻译单元时可能不确定。

`static` 局部变量的初始化是线程安全的（C++11 起），但之后的读写不是。

### 线程存储期

`thread_local` 的对象每个线程各有一份：

```cpp
thread_local int counter = 0;
```

它在所属线程开始时创建，线程结束时销毁。适合线程私有的缓存、错误状态、随机数种子等。

### 动态存储期

`new` 创建的对象有动态存储期，由程序员（或智能指针）决定何时释放：

```cpp
int *value = new int(42);
delete value;

auto owned = std::make_unique<int>(42);   // 推荐：自动释放
```

动态对象的生命期不由作用域决定，而由显式的 `delete` 或智能指针的析构决定。忘记释放会泄漏；释放两次是 UB；释放后继续使用是悬垂访问。

## 8.4 链接

链接决定“不同翻译单元里的同名声明是否指向同一个实体”。

### 外部链接

默认情况下，命名空间作用域的函数和非 `const` 变量有外部链接：

```cpp
int shared = 1;          // 外部链接

void bump();             // 外部链接
void bump() { ++shared; }
```

别的翻译单元可以用 `extern` 声明并访问：

```cpp
extern int shared;
void bump();
```

### 内部链接

`static` 或匿名命名空间让名字只在当前翻译单元可见：

```cpp
static int file_static = 200;

namespace {
int hidden = 300;
}
```

`static` 全局变量和匿名命名空间变量都是内部链接。区别主要在语法和名字修饰；现代 C++ 更推荐匿名命名空间，因为它对类型和函数也适用。

函数也可以有内部链接：

```cpp
static int helper() { return 1; }
```

### 无链接

局部变量、函数参数没有链接：它们只在一个作用域内存在，别的翻译单元根本看不到。

### 文件作用域 `const` 的特殊规则

C++ 里，命名空间作用域的 `const` 变量默认是**内部链接**：

```cpp
const int internal_const = 7;   // 内部链接
```

这是为了允许在头文件里定义常量而不违反 ODR。如果你要外部链接，加 `extern`：

```cpp
extern const int external_const = 42;   // 外部链接
```

`constexpr` 变量也默认内部链接。C++17 的 `inline constexpr` 可以在头文件中定义并保持外部链接。

### `inline` 变量（C++17）

C++17 之前，头文件里定义全局变量会导致多个翻译单元重复定义。常见做法是：

- 在头文件里 `extern` 声明，在 `.cpp` 里定义；
- 用函数返回静态局部变量；
- 用模板或宏绕开。

C++17 引入 `inline` 变量：

```cpp
// counter.h
inline int inline_shared = 7;
```

每个包含这个头文件的翻译单元都看到同一个 `inline_shared`，链接器会把它们合并成一个对象。`inline` 函数也是同样的道理：允许多个翻译单元里出现相同的定义。

`inline` 变量必须有**相同的定义**出现在所有使用它的翻译单元里；否则仍然是 ODR 违规。

## 8.5 `static` 与 `extern` 的多重含义

`static` 是 C++ 里最 overloaded 的关键字之一：

| 位置 | 含义 |
|------|------|
| 命名空间作用域的变量/函数 | 内部链接 |
| 局部变量 | 静态存储期，只初始化一次 |
| 类的静态数据成员 | 属于类，不属于某个对象 |
| 类的静态成员函数 | 没有 `this`，不能访问非静态成员 |
| 成员函数里的 `static` 局部变量 | 所有对象共享，只初始化一次 |

`extern` 的主要含义是“声明，定义在别处”：

```cpp
extern int shared;          // 声明
extern const int value;     // 声明一个外部链接的 const
```

`extern` 也可以和初始化一起出现，表示“这是定义，并且有外部链接”：

```cpp
extern const int external_const = 42;
```

不要用 `extern` 去“声明一个局部变量”，它只会让名字指向别处的对象，容易造成误解。

## 8.6 ODR：一次定义规则

**ODR**（One Definition Rule）是 C++ 程序结构的基本规则：

- 每个有外部链接的函数、变量、类类型、模板，在整个程序中只能有一个定义（模板和 `inline` 有例外）。
- 一个实体可以在多个翻译单元里**声明**，但只能**定义**一次。
- `inline` 函数和 `inline` 变量允许多个翻译单元里有相同定义，链接器负责合并。
- 类定义、模板定义可以出现在多个翻译单元里，但必须逐 token 相同。
- 违反 ODR 不要求编译器诊断；有时会表现为链接错误，有时会静默产生错误行为。

一个经典的 ODR 错误：

```cpp
// a.cpp
int value = 1;

// b.cpp
int value = 2;
```

两个翻译单元都定义了 `value`，链接时通常报 `multiple definition of 'value'`。解决办法：

- 只在一个 `.cpp` 里定义，其他文件用 `extern` 声明；
- 用 `static` / 匿名命名空间让每个翻译单元有独立副本（如果确实需要）；
- 用 `inline` 变量（C++17）。

### 头文件与源文件的分工

一个典型的多文件项目：

```text
counter.h     声明：extern 变量、函数原型、类定义、inline 函数
counter.cpp   定义：非 inline 函数、全局变量
main.cpp      #include "counter.h"，调用函数
```

头文件应该放：

- 函数声明；
- 类定义；
- 模板定义（通常）；
- `inline` 函数/变量；
- `constexpr` 常量；
- 类型别名、枚举。

源文件应该放：

- 非 `inline` 函数定义；
- 全局变量定义；
- 只在当前翻译单元使用的内部链接实体。

头文件保护：

```cpp
#ifndef COUNTER_H
#define COUNTER_H

// ...

#endif
```

或者用 `#pragma once`（非标准，但几乎所有编译器支持）。头文件保护防止同一个翻译单元重复包含同一个头文件；它不能防止不同翻译单元之间的 ODR 冲突。

## 8.7 静态初始化顺序问题

不同翻译单元里的全局对象，动态初始化顺序**未指定**：

```cpp
// a.cpp
extern int value;
int initialized = value + 1;

// b.cpp
int value = 42;
```

`initialized` 可能在 `value` 初始化之前运行，读到 0 或未定义的值。这就是**静态初始化顺序问题**（static initialization order fiasco）。

解决办法：

1. 尽量用 `constexpr` 做常量初始化，避免动态初始化。
2. 用函数局部静态变量，把初始化推迟到第一次调用：

```cpp
int &shared_value()
{
    static int value = 42;
    return value;
}
```

3. 用 `std::call_once` 或显式的初始化函数（在多线程场景下更复杂）。

函数局部静态变量的初始化在第一次执行到声明时发生，C++11 起保证线程安全。它不能完全消除所有顺序依赖，但能把“程序启动时”变成“第一次使用时”。

## 8.8 代码导览

本章是一个多文件程序：

- [`counter.h`](counter.h)：声明 `shared_counter`、`external_const`、`inline_shared` 和几个函数；
- [`counter.cpp`](counter.cpp)：定义 `shared_counter`、匿名命名空间里的 `internal_bumps`、`bump` 等函数；
- [`storage.cpp`](storage.cpp)：定义 `file_scope`、`file_static`、`internal_const`、`external_const`、`thread_local`、静态局部变量，并调用另一个翻译单元的函数。

编译：

```sh
make 08-storage/storage
./08-storage/storage
```

或者手动：

```sh
c++ -std=c++17 -Wall -Wextra -Wpedantic storage.cpp counter.cpp -o storage
```

输出里重点关注：

- `shared_counter` 在两个翻译单元里是同一个对象；
- `internal_bumps` 只能通过 `counter.cpp` 的函数访问；
- `inline_shared` 在头文件里定义，两个翻译单元看到同一个对象；
- `file_static` 和 `internal_const` 只属于 `storage.cpp`；
- 静态局部变量 `next_local` 跨调用保留值；
- `thread_local` 在当前线程里独立。

## 8.9 常见陷阱

| 写法 | 问题 | 建议 |
|------|------|------|
| 头文件里定义非 `inline` 全局变量 | 多个翻译单元重复定义 | `extern` 声明 + `.cpp` 定义，或 `inline` |
| 头文件里定义非 `inline` 函数 | 重复定义 | 加 `inline` 或移到 `.cpp` |
| 多个 `.cpp` 定义同名全局变量 | ODR 违规 | 只定义一次 |
| 依赖跨翻译单元的静态初始化顺序 | 顺序未指定 | 用函数局部静态或 `constexpr` |
| `static` 全局变量当共享状态 | 每个翻译单元一份 | 用外部链接 + 头文件声明 |
| 文件作用域 `const` 想共享 | 默认内部链接 | 加 `extern` 或 `inline` |
| 匿名命名空间里定义类型并在头文件暴露 | 类型不完整/不同 | 内部实现细节不要放头文件 |
| 头文件没有保护 | 重复包含导致重复定义 | 加 include guard 或 `#pragma once` |
| `delete` 后继续使用指针 | 悬垂，UB | 置空或使用智能指针 |
| 全局对象依赖另一个全局对象 | 初始化顺序问题 | 改为函数局部静态 |

## 8.10 语法卡片

| 术语 | 一句话定义 | 本章例子 |
|------|------------|----------|
| 存储期 | 对象存储的分配/释放时机 | 自动、静态、线程、动态 |
| 链接 | 不同翻译单元能否访问同一实体 | 外部、内部、无 |
| 翻译单元 | 一个源文件经过预处理后的结果 | `.cpp` + 头文件展开 |
| 外部链接 | 整个程序可见 | 非 `static` 全局变量 |
| 内部链接 | 仅当前翻译单元可见 | `static`、匿名命名空间 |
| ODR | 一次定义规则 | 全局变量只能定义一次 |
| `inline` 变量 | 多头文件定义合并为一个对象 | `inline int shared = 7;` |
| 匿名命名空间 | 内部链接的现代写法 | `namespace { ... }` |
| 静态局部变量 | 第一次执行时初始化，长期存在 | `static int count = 0;` |
| `thread_local` | 每线程一份的对象 | `thread_local int t;` |
| 静态初始化顺序问题 | 跨翻译单元全局对象初始化顺序未指定 | 用函数局部静态规避 |

## 8.11 练习

1. **多文件**：把本章程序拆成两个 `.cpp` 和一个 `.h`，自己写 Makefile，验证链接。
2. **链接实验**：把 `counter.cpp` 里的 `shared_counter` 改成 `static int shared_counter`，重新编译，读链接错误。
3. **`const` 链接**：在头文件里定义 `const int value = 42;`，在两个 `.cpp` 中包含它，分别打印地址，观察是否是同一个对象；再用 `inline constexpr` 对比。
4. **`inline` 变量**：在头文件里定义 `inline int shared = 0;`，两个翻译单元各加 1，打印最终值。
5. **匿名命名空间**：在 `counter.cpp` 里用匿名命名空间定义 `internal_bumps`，尝试从 `storage.cpp` 直接访问，读编译错误。
6. **静态局部**：写一个函数返回静态局部计数器，多次调用并打印地址，验证是同一个对象。
7. **初始化顺序**：构造两个全局对象，让一个依赖另一个，观察不同编译/链接顺序下的行为（不要依赖结果）。
8. **`thread_local`**：用两个 `std::thread` 分别递增 `thread_local` 变量，打印各自的值和地址（需要链接 `-pthread`）。
